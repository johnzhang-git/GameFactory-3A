# 游戏经济数值校准流程

适用于本仓库生成的所有**放置 / 增量类**游戏的数值调优。核心问题：设计文档里的参数是估算值，
而估算值经常与实现的实际行为不符——文档声称的机制可能根本没触发。

参考实现：`generated_games/gameE_card_collector/tools/balance-sim.mjs`
（首次应用的案例见 `gameE_card_collector/DESIGN.md` §7）。

## 0. 前置条件：为什么这套方法能成立

本仓库生成的游戏遵循「UI → Mechanic → 框架」依赖方向，纯逻辑模块（`catalog` / `economy` / `game`）
不依赖 three.js，可以用显式 delta 步进。**这是整条流程的前提**：同一份规则既能被帧循环驱动，
也能被一个循环脚本驱动，所以可以脱离渲染做上万次模拟。

如果目标游戏的经济逻辑与渲染耦合，先拆分，再谈校准。

## 1. 流程

### 步骤 1：写参数化镜像，但先证明它忠实

不要直接读生产常量做扫描——`ECONOMY` / `PRESTIGE` 是 `Object.freeze` 的，改不动。
在独立脚本里镜像一份规则，参数从配置注入。

**镜像不可信任，必须先用真实性校验（fidelity check）证明它。** 做法：用同一种子、
同一策略，同时驱动真实的 `CardCollectorGame` 和镜像，**每个 tick 比对全部可观测量**
（coins / cost / draws / unique / income / totalIncome），首个不一致立刻抛错。

```js
const drain = (canBuy, buy, open) => { while (canBuy()) { buy(); open(); } };
for (let i = 1; i <= ticks; i++) {
  game.update(INTERVAL); drain(...);   // 真实实现
  sim._step(INTERVAL);   sim._act();   // 镜像
  compare(i);                          // 逐项 assert
}
```

镜像一旦漂移就拒绝出报告。这样报告里的数字才敢用来做决策。

> 实践建议：镜像的默认参数**从真实模块读取**（`ECONOMY.COST_SCALE` 等），不要写字面量。
> 这样改了生产常量，模拟器自动跟上，不会静默脱节。

### 步骤 2：测量增长天花板——先找「什么时候停止成长」

**先问「玩家什么时候停止变强」，再问「一轮多长」。** 这两个答案常常相差一个数量级。

记录三个时刻：

| 指标 | 含义 |
|---|---|
| 集齐基础内容 | 短目标达成 |
| 收入停止增长 | **长目标的真正终点** |
| 成本墙到达 | 设计文案常声称的转生信号 |

如果「收入停止增长」远早于「一轮结束」，那么一轮的绝大部分时间是**等待，不是游玩**。
这是最重要的诊断信号，比总时长重要得多。

> 案例：卡牌游戏 19 张卡 **43 秒**集齐、**126 秒**全部满级，收入随即锁死 381/s。
> 一轮 30 分钟里增长期只占 **~5%**。

### 步骤 3：区分「闸门参数」与「兜底参数」

设计文档常把某个参数描述成节奏控制器，实际可能是别的角色。用一个反推公式验证：

```
若收入封顶为 I、成本每 COST_SCALE 累计收入 +1、墙阈值 W 秒：
   墙到达时间 T = COST_SCALE × (I×W − 初价) / I
```

> 案例：文档称成本墙在 ~30min 触发（每箱攒 10 秒）。反推得 `COST_SCALE ≈ 180`，
> 而实际值是 `1000` → 墙在 **2h47m**，一轮里**根本不触发**。`COST_SCALE` 其实是
> 「对永不转生的玩家兜底」，真正的节奏闸门是 `PER_POINT`（转生阈值）。

判断方法：**改这个参数，一轮时长会显著变化吗？** 不会的就是兜底参数。

### 步骤 4：参数扫描 + 跨种子验证

单一配置的结论不可靠。做二维网格扫描，并**换 6 个以上种子**确认结论不依赖特定随机流。

> 案例：`PER_POINT = 200000` 在 6 个种子下首次转生稳定在 **27m00s ± 5s**，命中 30 分钟目标。

扫描时同时记录「上限」列——低 `COST_SCALE` 会饿死玩家，导致内容练不满、
收入天花板达不到理论值，这时时长数字虽然好看但内容没被玩到。

### 步骤 5：报告「死亡时间」而不是总时长

总时长是误导性指标。要报告：

- 增长期占一轮的比例
- 增长停止到一轮结束的「纯等待」时长
- 玩家在一轮里实际做了多少个**决策点**

## 2. 实际踩过的坑

这些坑都真实产生过**错误结论**，记录以备复用：

| 坑 | 后果 | 规避 |
|---|---|---|
| **停止条件永远不触发** | 用了「每箱成本 ≥30 秒收入就转生」，实测该条件要 8h20m 才满足 → 模拟器跑到上限，报出「6 小时一轮」的假数据 | 遍历时 assert 停止条件在预期量级内触发；没触发就是策略假设错了 |
| **里程碑时间用整轮结束时间** | 成就达成时间全部等于轮末，四档解锁时间看起来一模一样 | 里程碑必须在**跨越那个 tick** 时记录，不能由轮边界推导 |
| **冷启动测试某策略** | 「只用黄金宝箱」从零开始：初始 20 金币买不起 30 的黄金箱，而卡池为空就没有收入 → 死锁，报出 0.00x 的假比值 | 对比策略必须**从同一起点分岔**，不能各自冷启动 |
| **拿解析 EV 当实测值** | 按基础收入算黄金箱是 1.94x；算上升级稀释后是 ~1.97x，但「3 次普通抽 vs 1 次黄金抽」的口径又不同 | 排序可信，绝对值必须实测；报告时标明是解析值还是实测值 |
| **只调时间轴就以为解决了问题** | 把一轮从 7min 拉到 27min，但增长期仍是前 1.5 分钟——只是等得更久 | 时长达标 ≠ 手感达标，两个指标分开报告 |

## 3. 检查清单

- [ ] 镜像已通过逐帧真实性校验（同种子、同策略、全部可观测量）
- [ ] 默认参数从真实模块读取，而非字面量
- [ ] 已测量「收入停止增长」的时刻，并与一轮时长对比
- [ ] 已反推验证：被文档称为「节奏控制」的参数是否真的控制节奏
- [ ] 停止条件在合理时间内触发（否则策略假设有误）
- [ ] 对比实验从同一起点分岔，而非各自冷启动
- [ ] 参数结论跨 ≥6 个种子稳定
- [ ] 报告了增长期占比 / 纯等待时长，而非只有总时长

## 4. 校准后必须回写文档

数值校准的产出不只是参数，还有**对文档断言的证伪**。凡是「文档声称某机制会触发」
的表述，都要用实测数据确认或标注为已证伪，否则下一个读文档的人会继续基于错误前提做决策。

> 案例：`gameE_card_collector/DESIGN.md` 原称「后期收入撞上成本墙，玩家感到变慢」，
> 实测证伪后保留原文并加 ⚠️ 标注实测数据与证伪结论，而非直接删除——
> 记录「曾经的错误假设」本身有价值。
